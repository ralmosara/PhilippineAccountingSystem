# Router migration plan — Hash router → @tanstack/react-router

## Status: planned, not yet executed

The frontend currently uses a hand-rolled hash-based router in [`src/app/router.tsx`](../src/app/router.tsx). It served us well up to ~13 pages but is now at the edge of its useful scope.

This document captures the migration plan so the next contributor can execute it without rediscovering the design decisions.

---

## Why migrate

| Pain point today | What TanStack Router gives us |
|---|---|
| Single 250-line `router.tsx` that grows linearly with every new page | File-based routes — each page declares its own route in its own folder |
| Route params are typed by hand via discriminated unions; easy to drift | Routes are type-safe; `useParams()` returns the exact type inferred from the path |
| No nested layouts (every page re-renders the TopNav from scratch) | `__root` + layout routes that wrap children, with their own loaders |
| No route-level data loading (every page does `useQuery` in `useEffect`) | Loaders run before render; pages get hot data on mount, no flash |
| Browser back/forward via `hashchange` only | Full history API + `<Link>` with prefetch on hover |
| RouteGuard repeats the FormRequest `authorize()` check at the page level | `beforeLoad` runs at route resolution — redirect/401 before any component mounts |
| Mostly-fine `lazy()` story by hand | Lazy loading per route by default; bundle size wins |

We already depend on `@tanstack/react-router@^1.79.0` (it's in `package.json` dependencies); no install step needed.

## Migration steps

1. **Install the router-plugin** (devDep): `@tanstack/router-plugin` + `@tanstack/router-vite-plugin`. Wire into [`vite.config.ts`](../vite.config.ts) before the React plugin.

2. **Create `__root.tsx`** with the existing `TopNav` + `<Outlet />` + auth-bootstrap. Move the `useBootstrapAuth()` call here; the splash/login state stays.

3. **Migrate routes alphabetically** — start with `dashboard` + one module (Tax was simplest in my dry-run). Each migration is ~10 lines:

   ```tsx
   // src/routes/tax/osd-elections.tsx
   import { createFileRoute } from '@tanstack/react-router';
   import { OsdElectionsPage } from '@/modules/tax/pages/OsdElectionsPage';

   export const Route = createFileRoute('/tax/osd-elections')({
       component: OsdElectionsPage,
       beforeLoad: async ({ context }) => {
           if (!context.auth.hasPermission('tax.osd_election.view')) {
               throw redirect({ to: '/' });
           }
       },
   });
   ```

4. **Replace `<a href="#/...">` with `<Link to="...">`** across all components. The migration codemod from TanStack docs handles ~80% mechanically.

5. **Drop `hashchange` listeners** — `useNavigate()` + `<Link>` use the history API. The hash routes (`#/accounting/journals`) become real paths (`/accounting/journals`), which means **the backend's Vite dev-proxy must catch all non-/api routes and serve `index.html`** (already configured per existing `vite.config.ts`).

6. **Delete `src/app/router.tsx`** once `routes/` is complete. Update `App.tsx` to render `<RouterProvider router={router} />`.

7. **Run `tsc + lint + test`** — there should be no type drift because page components were untouched. The route-tree generator runs as part of `vite build` (the plugin emits `routeTree.gen.ts`).

## Risks + mitigations

| Risk | Mitigation |
|---|---|
| Old bookmarks (`#/sales/invoices/abc`) break | Add a redirect in `__root.tsx`: read `window.location.hash` once at mount, `navigate(hash.replace(/^#\//, '/'))` if it's non-empty |
| Permission-gate logic duplicated between `beforeLoad` and FormRequest | Already duplicated; the migration doesn't make it worse. Long-term fix is a `/auth/permissions` GraphQL fragment, out of scope |
| Bundle size regression | Code-splitting per route should *reduce* initial JS by ~30%; verify with `vite build` before/after |
| Type-safe params require shipping `routeTree.gen.ts` | Add to `.gitignore` and regenerate via `npm run build` — same pattern as Prisma's `client.ts` |

## Estimate

The migration is mostly mechanical. Per-page work is ≤10 minutes. With 21 pages + the root layout + the migration commit:

- Setup (plugin + vite + root): 30 min
- 21 page wrappers: ~3.5 hours
- `<a>` → `<Link>` codemod + manual review: 1 hour
- Test + lint + verify: 30 min

**Total: ~5–6 hours of focused work.**

Worth doing the next time someone needs to add a 4th level of nesting (e.g. an invoice line editor that shouldn't redraw the customer header). Until then the hash router is fit for purpose.
